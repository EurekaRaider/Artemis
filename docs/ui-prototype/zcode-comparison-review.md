# ZCode 界面设计调研报告与 Artemis 方案 1 改进建议

调研日期：2026-09-07。调研对象：ZCode 界面、Artemis `components.html` 方案 1（方向 A）及 `artemis-ui.html` 工作区原型。文档状态：调研与建议，尚未实施。

## 调研摘要

**建议保留方案 1 的中性底、系统字体和圆角体系，优先重建「画布—工作面—输入区」层次，再拆开品牌色与主按钮颜色。** 当前沉闷感主要来自色彩角色合并、内容文字过度弱化，以及组件组合后视觉重量趋同。

组件页与整页原型之间存在可核对的差异：深色工作区与 Composer 同为 `#262626`；组件页 Composer 使用浮层阴影，工作区则没有阴影。因此，只沿用组件色板和圆角，无法保证完整工作区具有同样的层次。

## 调研目标与方法

本次调研回答三个问题：ZCode 如何组织主布局及深浅主题；方案 1 应用到工作区后为什么显得死板、沉闷；哪些调整能以较小改动改善实际使用界面。

研究范围包括主画布、侧栏、Dock、对话内容、Composer、工具记录、审批卡，以及字体、边框、圆角、阴影、状态和交互配色。执行策略和权限模型不属于改造范围。

采用以下方法：

1. 查阅 ZCode 官方文档、产品截图和官网演示样式，使用浅色实测截图补充双主题观察。
2. 在浏览器中检查 Artemis 方案 1 的深浅组件页、工作区及深色 Review 分栏，读取关键元素的计算样式。
3. 对照共享 token、兼容映射和页面组合 CSS，定位视觉结果与设计说明之间的差异。
4. 计算代表性文字色与背景的合成对比度，并结合项目已有分级门限解释可读性问题。
5. 按视觉收益与改动范围提出 P0、P1、P2 建议，给出建议配色与后续验收方法。

## ZCode 值得借鉴的设计逻辑

### 布局：任务优先，工具按需出现

浅色实测图顶部的侧栏入口是新建任务、搜索、技能，下方才是项目和任务。中间以对话和输入区为核心；官方文件预览图显示右栏打开后，用独立标签与文件路径承接代码阅读。

这与 Artemis 的两栏加 Dock 架构兼容，没必要重做导航框架。但 Artemis 目前把插件市场、用量、定时任务、归档放在侧栏最上方，而新建会话藏在项目行操作里；视觉上先看到管理功能，主工作入口较弱。建议让常用创作入口更容易发现，管理入口保持紧凑。这是信息优先级建议，不是要求复制 ZCode 的全部功能。

官方深色截图中的侧栏受材质、平台和版本影响，有时比主区亮；官网演示则定义了更深的 sidebar。不能把「侧栏永远最黑」理解成 ZCode 的普遍规则。稳定的原则是主画布、导航与可操作面具有不同的角色。

### 深色：深画布承托稍亮的操作面

官网 `.hero-visual-theme` 的部分定义：

| 角色 | 官方演示定义 |
| --- | --- |
| 主画布 / header / panel | neutral-900，约 `#171717` |
| sidebar | neutral-950，约 `#0a0a0a` |
| card / popover / input | neutral-800，约 `#262626` |
| 主按钮 / 按钮文字 | neutral-50 / neutral-950 |
| 品牌 | sky-500，独立于 primary |
| 输入焦点边框 | brand |
| selected | 白色约 10% 混合 |
| 普通 surface | 白色约 5% 混合 |
| 文件 / 技能 / 命令节点 | sky / violet / amber，各有淡底、前景和 hover 色 |

灰阶决定空间关系；蓝、紫、琥珀承担引用类型及交互含义。黑白主按钮不意味着所有强调都必须黑白。官方任务管理也为用户分组提供颜色，但这些身份颜色应与成功、警告、失败状态分开理解。

新建任务截图里，大面积画布很安静，稍亮的输入区成为视觉中心；项目与分支是轻量图标文字触发器，并没有给每个上下文项都加一个强烈的小框。

### 浅色：浅灰画布、白色输入区、清晰正文

浅色实测截图呈现偏中性的浅灰工作底、略有区别的侧栏和白色输入区。用户消息使用轻灰填充，助手内容直接排在画布上；文字主次主要由正文深度、字重、段落和列表形成。

它仍然非常克制，并非靠大量彩色块消除沉闷。比较有用的是：输入区比画布亮；长篇答案保持正常正文强度；侧栏不堆叠大量独立卡片。截图中的 emoji 是回答内容，不应推导成全局图标设计规范。

## 方案 1 为什么组合后显得死板

### 1. 深色主区使用了本该属于卡片的颜色

浏览器计算样式：

| 元素 | 当前浅色 | 当前深色 |
| --- | --- | --- |
| `.workspace` | `#ffffff` | `#262626` |
| `.conversation` | 透明，露出 workspace | 透明，露出 workspace |
| `.composer` | `#ffffff` | `#262626` |
| `.composer-topbar` | `#f5f5f5` | `#303030` |
| `.user-message` | `#e5e5e5` | `#3d3d3d` |
| `.sidebar-main` | `#f5f5f5` / 72% | `#0a0a0a` / 92% |

`ui/tokens.css` 已定义深色 `--bg: #171717`，但 `workspace/workspace.css` 的 `.workspace` 使用 `--surface`，后面的 `.conversation` 又变成透明。所以主工作区实际铺成 `#262626`，与输入框同色。工具卡使用 `--bg`，反而成为一个深色洞；上下文顶条比输入主体更亮。

**相同色板不等于相同视觉效果：ZCode 演示中的深画布与亮输入框，在这里变成了亮画布与同色输入框。**

### 2. 主操作、品牌、信息与焦点挤在一个 accent 中

`ui/tokens.css` 的 A 方向将 accent 定为浅色 `#0a0a0a`、深色 `#fafafa`。`ui/compat.css` 再从它派生 `--accent-soft`；`ui/artemis/catalog.css` 的 `.badge.blue` 也引用 accent。

结果是原本名为 blue 的信息徽章、开关、进度、链接和部分选中状态一起走灰阶。组件页文案仍写着「Artemis Blue」「开关品牌蓝」，与实际颜色不一致。

应保留黑白主按钮，另设 brand、info 和各类 content reference 角色，不能只把 accent 改蓝后全站替换。

### 3. 组件页与工作区的 Composer 并不是同一个视觉样本

实际读取浅色 Composer：组件页有 `0 12px 40px rgba(0,0,0,.16)` 加第二层阴影；工作区为 `box-shadow: none`。组件页外围还有展示卡、内边距和深浅背景对照，工作区中这些承托条件消失。

这解释了为什么组件单独看有体积，放进页面后变平。建议统一为明确的 Composer 组合变体，采用轻微、专用的输入区阴影；不把弹窗级大阴影复制到整个工作区。

### 4. 视觉重量分配失衡

实际工作区里，品牌图标、版本标签和审批按钮是醒目的黑白实心块；正文说明、项目名、文件名及输入区控件却普遍较淡。Composer 又堆叠目标状态、灰色上下文横条、三枚小按钮、附件芯片、输入区、底部策略与模型控件。

工具记录和审批卡也有相近的宽度、圆角、边框及分隔线。主区因此像一串同等级表单容器，阅读过程、当前活动和下一步操作没有足够明确的分工。

### 5. 淡文字是刻意决策，但仍有可读性代价

当前 README 记录了用户批准的项目分级门限：primary 4.5、secondary 3.0、tertiary 2.2。本审查尊重这条现有合同，不把它误报为实现回归。

按 token 与实底做 sRGB alpha 合成，浅色 text-2 在白底约为 **3.35:1**，text-3 约为 **2.46:1**；深色 text-3 在 `#262626` 上约 **2.60:1**。这些数值可解释「发灰」感，即使满足项目自定义分级门限。

建议将需要连续阅读的说明和文件名提升到正文或明确的 secondary 色；tertiary 只保留给非关键元信息。组件页仍有「文字全部 ≥4.5」等旧说明，应与当前决策对齐。现存 `contrast/REPORT.md` 还记录了普通主题失败项及等价声明失效，属于既有证据，不能视为本次重新跑过的结果。

## 推荐的 A 方案调整

### P0：先改色彩角色与页面层次

以下是 **Artemis 建议起点**，不是 ZCode 精确取色，也不是已经通过验收的最终 token。

| 语义角色 | 建议浅色 | 建议深色 | 使用规则 |
| --- | --- | --- | --- |
| canvas | `#fafafa` | `#171717` | 对话背景与主阅读区 |
| navigation | `#f3f4f5` | `#141414` | 侧栏；保留材质时核对最终合成色 |
| panel | `#ffffff` | `#202020` | Dock / 工作面 |
| composer | `#ffffff` | `#262626` | 输入主体，必须与 canvas 有层次 |
| popover | `#ffffff` | `#2b2b2b` | 菜单、浮层，配专用阴影 |
| user-message | `#f0f1f2` | `#303030` | 降低大块消息底色的重量 |
| text-primary | `#27272a` | `#e5e5e5` | 正文、当前任务、重要文件名 |
| text-secondary | `#60646c` | `#a8a8ad` | 辅助说明与普通控件 |
| text-tertiary | `#717680` | `#898990` | 时间和非关键元信息，仍须按底色检查 |
| action-primary | `#171717` | `#f5f5f5` | 主按钮，反色文字 |
| brand / focus | `#0369a1` | `#38bdf8` | 链接、焦点、当前任务的小面积标记 |

灰阶底色变化尽量保持小幅；先保证角色分离。上述建议用不透明文字色减少不同背景上的合成漂移，并不要求推翻现有分级对比合同。

具体落点：在 `ui/tokens.css` 建立语义角色，通过 `ui/compat.css` 做必要的兼容映射；`workspace/workspace.css` 中 `.workspace` / `.conversation` 指向 canvas，Composer 指向 composer，Dock 指向 panel。避免继续在文件末尾追加同名 selector 覆盖。

### P1：让 Composer 成为明确的输入中心

1. 保留 16–18px 的输入区圆角；常规工具卡用 10–12px，菜单用 10px 左右。圆角应表达容器级别，不让所有区域都像同尺寸卡片。
2. 项目、分支、模式改用透明的图标文字触发器，hover 才出轻底；审批策略保持清晰可见，不改变任何权限语义。
3. 上下文顶条与输入主体只差半档明度，减少强分隔；附件行有内容才出现。
4. 附件类型可用蓝色文件图标、紫色技能标记等小面积识别色；不把整个附件区染色。
5. 浅色给 Composer 很轻的接触阴影和中远距阴影；深色主要靠稍亮填充、柔和描边，阴影仅辅助。新增 `shadow-composer` 专用规则，并同步组件页与工作区。
6. 黑白发送按钮保留。禁用态继续明确，不能为制造视觉重点而让不可用按钮看起来可点。

### P1：降低历史记录重量，突出当前活动

已完成工具调用优先收成一行摘要，保留数量、完成符号和展开入口；当前运行项可展开，异常及审批保留必要信息。工具展开区采用平面的列表和轻分隔，减少「外卡—表头—逐行边框—徽章」重复层级。

色彩角色建议：运行中使用小面积 info 蓝及运行图形；成功用绿加完成符号；等待确认用琥珀加明确文字；失败用红加错误图标。用户自定义项目色、Agent 身份色与这些状态色分开。此项改变展示方式，不改变状态流转或执行授权。

### P1：重排视觉焦点与阅读节奏

正文建议从当前 14px 试到 15px，中文行高约 1.65–1.75；文件和命令 12–13px 等宽，侧栏 12.5–13px，关键状态不使用最淡一级。版本号降为普通元信息，不长期占用与主按钮相同的实心强调。

当前宽屏实际 viewport 为 1864 CSS px，主区 1604px，而对话列仍是 760px（Composer 主体 720px）。限制阅读宽度本身合理；沉闷感不宜通过无条件拉宽来修复。建议先完成字体和层次调整，再在大窗口试验 800–840px 上限；Dock 打开时维持可读的对话最小宽度与可拖动比例，不把整个区域填满卡片。

### P2：补齐组合规范

在组件方案中增加同一套「工作区切片」：正常对话、工具运行、等待审批、Review 分栏、空态，每个切片同时提供深浅主题。将各组件单独好看，提升为整页组合后有稳定主次。

为 surface、button、badge、reference、focus、hover、selected 分别明确角色。hover 与 selected 不能只靠相近的填充区分；保留文字强度、选中标记及 ARIA 状态。对实际采用的轻阴影例外写明用途，并清理与实现矛盾的「品牌蓝」「全部 ≥4.5」「阴影仅浮层」说明。

## 建议落地顺序与验收

先做 P0 的 canvas / panel / composer 映射与品牌角色拆分，通常是视觉收益最大的最小切片。随后简化 Composer 和工具记录，再考虑侧栏入口顺序。不要同时扩展新配色方向、换字体系统和大改导航。

后续实施验收应包括：同内容同视口的深浅前后对照；组件页与工作区 Composer 同一变体的计算样式；Dock 关闭和打开；键盘焦点与菜单展开；长中文和长文件名；普通及增强对比度。按项目已有门限运行对比矩阵，并针对角色分配核对重要信息是否被错分为 tertiary。
