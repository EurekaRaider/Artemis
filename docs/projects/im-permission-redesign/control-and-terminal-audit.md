# 查询默认权限、任务取消与拒绝终态复查

日期：2026-09-18。检查基线：`8fcbed4`，包含权限重构 `1c6b36d`。修复分支：`codex/im-control-terminal-audit`。

本次按用户确认的“两端均已更新”排查。产品要求是：已启用会话默认可以查询配置范围，取消自己的任务不依赖文件访问授权，队友拒绝后本次任务结束。

## 现场证据

- 本机 `/Applications/Artemis.app` 的安装包时间为 10:10，主进程 10:11 启动；包内包含写操作排队及语义取消代码。不是只检查源码而忽略运行版本。
- 10:16 的真实请求中，Jupiter 查询成员、发送委派，再调用等待工具。
- 10:17 收到 Solar 的 `rejected`，原文是“请在桌面确认此会话的数据与分享范围后继续。”这对应接收端对范围确认状态的检查，发生在读取目录之前。
- Jupiter 的等待工具已返回 `state: interrupted`，本地回合随后完成，线程为 `idle`。因此截图里的“现在等待它的结果”并不是远端仍在执行的证据，而是回合完成回传复用了较早的模型文本。
- 本机当前群范围已确认，配置为整个项目可读。未读取 Solar 的数据库；不能进一步断言它的确认状态为什么被清零。用户确认 Solar 也已更新，本次不将旧版本作为解释。
- 实际用户数据库仅用于只读检查，没有改写已有授权、任务、凭据或历史消息。

## 根因与修复

| 路径                                 | 原有问题                                                                        | 修复后的行为                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 任务启动、读取、回传                 | `requireImScope` 把执行确认作为所有操作的前置条件；Gateway 同步也排除未确认范围 | 已启用项目/会话的配置读取范围默认有效；查询及结果回传不要求再次确认写入权限                                     |
| 写入与 Shell                         | 原来依赖统一入口阻断，直接删除入口检查会连同写操作一起放行                      | 在实际写入及命令操作前单独校验确认状态；给 Agent 的能力描述也隐藏待确认的写入及 Shell                           |
| 目录与文件边界                       | 放行默认读取后仍需保留文件根的类型边界                                          | 保存时对所有可读范围检查文件/目录类型，保留目录投影、路径穿越、受保护文件与链接隔离                             |
| 真人 `/status`、`/stop`、`/stopwait` | 查询/停止自己的任务仍经过项目数据授权；群成员在 Gateway 入口即被拒绝            | 单独校验设备、平台身份、会话和任务归属；数据授权失效后仍可查询基本状态、停止本地工作与等待                      |
| 自然语言取消                         | 仅主人且已有运行/等待任务时才做语义分类；接收失败后的“取消任务”被当成新的任务   | 群成员可取消自己发起的任务；没有可取消任务时返回明确的空状态。语义分类失败仍不擅自取消；显式 `/stop` 不依赖模型 |
| 向队友取消                           | Desktop 和 Gateway 的取消路径都要求数据授权，过期后无法发送                     | 取消仅提交无任务正文的控制帧，继续验证原工作流及任务归属；非取消命令仍要求当前数据授权                          |
| 队友取消回执                         | 接收方已经停止，但回执沿用旧数据授权，可能停留在 `cancel-sent`                  | 经认证的取消回执只发送固定状态文本，可在数据授权失效后返回；收到回执才认定远端已取消                            |
| 队友拒绝/失败/取消                   | 已结束等待的通知不是终态；随后回合完成又回传旧的“等待”文本                      | 持久记录被中断的回合并发出一次明确终态，抑制该回合迟到的进度/完成回传；群活动和状态查询同步显示中断             |
| 等待入口竞态                         | 自动等待已存在时，首次 `wait` 可能继续使用拒绝回执之前的快照                    | 先用最新任务状态刷新自动等待，再决定继续等待或结束                                                              |
| 显式重试                             | 终态抑制标记不能误伤用户主动重试                                                | 只清除获批重试回合的标记，旧回合仍禁止自动续跑和再次派工                                                        |

## 保留的边界

- 默认查询以已经启用的项目和分享对象为边界。已有选定目录、单个文件范围不会扩大成整个项目；空读取根按产品默认规则表示整个项目，受保护内容仍排除。
- 项目撤销、过期、群身份变化仍阻止项目读取、旧内容回传和新的派工。基本状态与停止控制不携带项目内容。
- 普通群成员只能控制属于自己、位于当前会话的任务；原发起人的控制身份持久保存，其他成员追加或排队消息不能取得该任务的取消权。主人保留其机器人任务的控制权；项目切换和审批仍属于主人管理操作。
- Plan/Review 的写入与执行限制、审批快照、受众校验、任务去重和协议身份验证保持有效。
- 拒绝、失败、取消后不会自动重派。超时仍表示远端状态未知；结束本地等待不等于确认远端停止。
- 首次启用新的群仍需确认分享对象。权限界面的 14 种语言提示已明确区分默认查询与待确认执行能力。
