# 群协作权限体系重新评估

日期：2026-09-18。评估基线：`da15c4a`。状态：核心改造已实施，源码与本机隔离验证完成；真实双机验收待进行。用户现有授权和已安装应用未被修改。

后续复查：[查询默认权限、任务取消与拒绝终态](./control-and-terminal-audit.md)。其中更新了默认读取与执行确认的分离规则，并记录真实失败回执和控制路径遗漏。

## 1. 结论与目标

当前主要问题是权限检查的粒度、配置完整性和失败后的处理方式：一个动作失败容易扩大成整个任务停止，一次配置变更容易影响多个受众，授权界面显示的能力与执行环境实际支持的能力存在差距。

建议以“项目 × 群 × 动作能力”的持久授权为中心。主人一次确认协作边界；系统在每次操作时自动校验；正常协作在边界内持续运行；权限扩张和高风险动作才打断用户。

目标路径：主人启用群协作并确认项目范围 → 群成员 @ 机器人 → 已授权机器人之间委派和补充需求 → 各自在本机授权范围执行 → 结果返回原群 → 原任务继续。日常路径不需要反复回桌面设置。

安全目标包含保密性、文件完整性和任务可用性。不能以增加弹窗代替执行隔离，也不能以“机器人可信”代替接收方自己的权限检查。

## 2. 评估阶段的证据及边界

- 检查了 Desktop broker、`ImService`、文件策略、原生 Shell 策略、Agent 工具过滤、Gateway 群路由和机器人协作协议。
- 只读检查本机 `im.sqlite` 的有效 `settings-v2`，未读取凭据正文、未修改用户配置。唯一项目授权已开启 Execute、automatic、Shell 和网络，未过期且已确认。
- 配置含 3 条群授权记录，仅 1 条有对应群数据范围；另 2 条需要在修复界面中区分“仍有效但缺范围”和“已失效”。不能直接删除或自动复制本人范围。
- 已有群范围包含 33 个显式读取根和相同的写入根，不属于“整个项目可读”。按当前策略，读取 `.` 会被拒绝，即使这些根来自用户曾经的全选操作。

## 4. 目标权限模型

### 4.1 对用户只呈现三个层次

1. **谁可以发起和接收**：指定群、真人发起规则、允许协作的机器人。主人保留修改授权的权力。
2. **可做什么**：查看项目、协作修改、运行受控命令；联网目标与文件分享作为明确能力。
3. **何时需要确认**：扩大范围、增加外发对象、发布或部署、访问凭据、破坏性操作、策略无法确定的命令。

群授权界面提供“只读讨论”和“协作开发”预设，并展示实际授予的能力。预设用于创建可理解的草稿；主人保存时确认一次。已有用户不会在升级后被自动切到更宽权限。

“协作开发”预设可以包含：经主人选择的整个项目或目录内读写、已授权伙伴委派、受控构建测试、向同一已确认群返回结果。联网默认仍受限制，不因选择开发预设而自动继承个人凭据或通用网络。

### 4.2 后端保留强制检查

有效能力由以下条件共同决定：真实平台身份与群路由、接收方本机授权、当前任务模式、当前操作资源、交付受众、系统可执行边界。

- 发起方有权派工，不等于接收方允许执行。接收方只使用本机项目和本机数据范围。
- 本机可读的数据不自动成为可发到群的数据。共享任务只引入对当前受众可分享的项目内容；私人历史、凭据和其他任务上下文不混入。
- 委派任务继承工作流的接收对象限制、有效期、预算和取消状态；不传递发起方的文件系统权限。不同机器使用自己的路径映射。
- Pi 仍是唯一 Agent 循环。Plan/Review 保持不可写、不可派工；需要执行时显示一个明确的模式切换入口。
- 每次操作执行前检查，异步写回及外发前再次检查撤销状态。减少用户点击不等于删除这些检查。

OWASP 的依据是最小权限、默认拒绝和逐请求校验；本方案据此把常规校验交给系统，把人审集中在高风险与权限变化上。[授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)、[Agent 与提示注入防护](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

## 5. 日常动作如何处理

| 动作                                            | 目标处理               | 保留的边界                                                 |
| ----------------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| 查询当前群成员、自己工作流的状态                | 自动                   | 身份、群和任务归属检查；不暴露其他工作流内容               |
| 保存等待、接收已派任务结果                      | 自动                   | 等待与执行状态持久化；不把沉默当作失败                     |
| 读取授权文件、浏览目录                          | 自动                   | 只返回范围内内容和名称；链接、穿越、敏感项仍拒绝           |
| 修改授权目录内普通文件                          | 开发预设下自动         | Execute、写入范围、版本冲突检查和变更记录                  |
| 给已授权且验证通过的机器人委派或补充任务        | 自动                   | 接收方独立授权、受众检查、任务归属、幂等和预算             |
| 调用已配置的构建、测试工具链                    | 在受控运行环境内自动   | 无个人凭据、隔离缓存、限制网络、受限写回；脚本不是天然可信 |
| 向原群发送该群授权内容的摘要和结果              | 自动                   | 内容来源、当前受众、撤销和敏感数据检查                     |
| 首次添加群/机器人，扩大读写范围，开启新网络目标 | 主人一次确认           | 确认具体新增能力，不重新确认无关群                         |
| 发布/部署、跨群外发、访问凭据、无法约束的命令   | 明确确认或专用能力入口 | 不用通用“自动批准”绕过执行隔离                             |
| 用户取消自己的任务                              | 及时停止并显示实际回执 | 不能取消无关任务；取消后禁止自动重派                       |

`wait` 会修改内部等待记录，但不应因为这种内部持久化而要求用户再次批准。`cancel` 有控制副作用，需要任务所有权检查；可复用当前明确取消请求，不逐次弹审批。

## 6. 四项关键改造

### 6.1 把“访问被拒绝”缩小到具体动作

当模型请求项目根目录时，若只授权 `src/` 和 `docs/`，返回仅由这两个授权根构成的视图；不枚举或泄露其他根名称。可同时提供由权限记录生成的 `capabilities`，让模型预先知道有效范围和工具能力。

普通越界返回结构化错误，包含失败操作、缺少的能力、合法替代范围和恢复入口。任务可继续已经合法的工作；不可换 Shell/Python 读取同一被拒资源。该规则由所有文件及 Shell 执行路径共同强制，不依赖提示词。

真正需要暂停整个相关任务的情形：授权被撤销、身份或群路由失效、受众改变、执行隔离失效。系统权限故障、工具链缺失、项目锁等待、网络不可达分别显示，不再统一要求用户扩大分享范围。

如果所缺能力是任务必需条件，只挂起依赖该能力的工作分支。主人补齐权限后在原任务恢复；同一缺口合并成一项请求。恢复不重放已经执行的写入或发送。

### 6.2 统一“已授权”与“实际能执行”

范围模型用显式的 whole-project / selected-paths 表达；选定目录涵盖其未来普通文件，文件授权仍绑定文件类型。旧的“全选当前条目”按原语义迁移，不能默默变成整个项目写入。

按类别保护文件：

- 凭据及宿主控制数据：持续强制保护，不因整个项目授权开放。
- 普通隐藏配置、项目文档、工具入口：按明确项目范围处理。项目文档中的指令不能提升权限。
- `.github` 等影响发布/CI 的配置：可提供项目读取，写入按工作流修改能力单独控制。
- `.git`：避免开放整个目录；通过宿主 Git 能力提供状态、差异、历史等需要的操作，过滤远端凭据和配置。提交与发布分别授权。

Shell 不再仅显示一个开关。启用时预检运行时、沙箱、可写目录和缓存；界面直接显示“可运行 Node 测试”等经过验证的能力。

运行时目录只读挂载，临时目录与缓存归当前任务，清除个人环境和启动脚本。优先使用受控运行目录和经过检查的变更写回，避免为包管理器直接开放整个 Homebrew 或用户目录。`npm test` 等命令可执行任意项目脚本，不能仅凭命令名认定安全。

联网能力区分构建依赖下载与业务外发，逐步使用宿主代理或受控工具约束目的地、重定向和内网访问。现有 network 布尔值允许通用出站网络，不能声称已有域名限制或完整防外泄能力。正则秘密扫描只作为补充。

### 6.3 把版本失效限定到实际变化

身份/群路由、某受众的数据范围、伙伴许可、显示名称分别处理。群名修改不失效；一个群范围变更不打断其他群或私人授权；增加读取范围可更新原任务的后续能力，旧动作仍须重新检查。

撤销、缩小范围和新增实际接收者需要特殊处理：停止受影响的执行或交付，拒绝旧凭据/旧审批重放。已经进入模型上下文的数据无法靠修改权限抹去；范围收窄或受众扩展时，可保留用户可见任务历史，但为后续执行建立干净上下文，只带经验证可共享的交接内容。

真实群消息对整个群可见。机器人许可名单不等于全部消息读者；新增群成员的分享风险不能通过“只校验机器人”解决。需要明确选择“信任这个动态群的成员”还是“固定受众变化后确认”，并展示这一差异；默认不能静默扩张已有受众。

平台返回部分名单或暂时无法刷新时，保留已有身份记录并显示未知状态；不能将未知成员当成不存在。严格固定受众模式下，无法确认接收者时暂停交付，不扩大到停止全部安全本地工作。

### 6.4 让并发成为调度问题

成员查询、进度、等待和委派不占文件写锁。写入在实际执行阶段获取锁，冲突时自动排队并显示等待原因。

先保持同一 checkout 的写操作串行；能明确计算范围时再允许不相交写入并行。任意 Shell 的潜在写范围不明确时，保守持有执行期写锁。跨调用的“读—改—写”使用版本或哈希检查避免覆盖别人的新修改；需要一致视图的分析使用快照。

不将用户的本地任务默认改成托管 worktree；临时命令运行目录属于执行隔离，不改变现有任务工作区选择。

## 7. 设置和故障恢复

权限统一放在“设置 → 消息接入 → 项目与协作权限”。项目行的“授权配置”是唯一权限编辑入口，主人单聊与群范围在同一弹窗中设置；任务侧栏只显示状态并跳转到此入口。原来单独的群协作设置页面和第二套群文件树已移除。就绪状态至少覆盖群路由、项目范围、执行模式、伙伴许可/证明、工具链支持。

Desktop 与 Gateway 分属不同持久化边界，不能假称单一数据库事务。采用草稿/待激活 → 两侧验证并持久化 → 激活流程，幂等重试；部分保存失败保留原有有效授权并显示需要修复的部分。

现有配置检查提供明确修复：缺 scope 的有效群由主人选择范围；失效群记录可定向移除。修改哪个群，就只确认那个群，不借此隐式确认其他受众。

错误示例：“接收方机器人缺少本群对 `reports/` 的写入授权；其他已授权工作仍可继续。”主人在可信桌面或经过身份校验的专用审批入口处理。同一群的其他成员不能通过回复“同意”给本机提权。

机器人互信必须仍由主人授予；系统自动完成授权伙伴的通信验证、有限重试和恢复。通信探测可重试，已经被用户取消或结果未知的实际任务不能自动重派。

## 8. 实施顺序与验收

每阶段先补行为和安全回归，再调整实现。现有安全测试中有少数把“全任务冻结”当成预期，需要改成验证具体越界始终被拒，且合法操作仍可继续。

| 阶段                 | 修改范围                                                      | 完成条件                                                                                                           |
| -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| P0：消除任务连锁阻塞 | `im-policy.ts`、`im-service.ts`、`main.ts`、`remote-tools.ts` | 有限目录可导航；一次越界不冻结合法读取/状态/等待；读操作不因无关写任务被误判无权；错误明确分类                     |
| P1：统一群授权与恢复 | `im-security.ts`、Gateway 群/协作策略、权限设置 UI            | 每群完整授权记录；单群变更隔离；群名变化不打断；主人一次确认即可启用；原任务补权后恢复                             |
| P2：让开发命令可用   | `im-sandbox.ts`、Windows 文件/命令组件、工具链能力展示        | 指定真实项目可完成安装依赖、构建和测试；缓存/运行时可用；凭据、跨目录和出站边界仍被强制执行                        |

## 9. 已实施内容与验证

- 目录导航返回授权根的投影视图，不枚举未授权条目；越界只拒绝当前操作，合法工作继续。旧阻塞记录不会在启动时批量清除，具体任务的新操作仍须重新通过当前身份、模式、范围和有效期检查。
- 成员/状态查询、等待和取消不再进入逐次审批；派工、写入及命令仍服从项目的 ask/automatic 策略。Plan/Review 的执行禁令保留。
- 写入和命令按项目执行期排队。等待过程中可以取消，并在真正执行前重查授权。文件读取返回内容哈希，写入支持哈希或“必须不存在”的前置条件，防止覆盖已发生的并发修改。
- 确认状态和操作版本按受众保存。改一个受众不使其他受众失效；旧数据兼容读取但不会自动扩大授权。只增加读取范围保留模型上下文；缩小读取范围建立干净上下文并保留用户界面历史。旧审批和旧交付仍按操作版本失效。
- 群显示名称修改不轮换权限版本。已授权伙伴最多自动探测三次，使用 1 分钟 / 5 分钟退避并持久化预算；手动探测仍受 30 秒冷却限制。不会自动重派实际任务。
- 整个项目写入是新的显式能力，包含未来普通文件。旧“全选条目”保持原来的选择语义；主人必须重新确认才能选择项目级写入。
- 文件工具与 macOS 命令均继续保护凭据、私钥、控制配置和链接边界；普通隐藏目录、构建缓存和环境示例文件可在授权范围内使用。Windows 文件代理支持显式项目写入，命令的隔离副本仍按授权检查写回。
- macOS 命令只读开放已发现的 Node 二进制、确切原生依赖与 npm 代码目录；采用独立 HOME、临时缓存及空 npm 配置，不继承个人环境和凭据。无法识别的运行时不会获得更宽目录权限，基础系统命令仍可用。
- 权限编辑只保留项目行的“授权配置”。弹窗通过“分享给谁”切换主人单聊、已启用群、新群和暂停群，使用同一范围表单；新群和恢复接入仍须独立确认。群列表只显示状态、打开对话和暂停操作，不再提供项目选择、范围表单或授权按钮。设置页不再显示群成员列表。相关文案覆盖 14 种语言。
