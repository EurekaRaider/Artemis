# Artemis 设计模式落地解决方案

> **文档定位**：基于 `docs/design-mode-proposal/` 下两份 Open Design 调研报告（`open-design-research-report.md`、`open-design-deep-research-report.md`）与 Artemis `codex/design-p0` 分支现状基线，给出设计模式的产品解决方案与分阶段路线图。配套页面级规格见 [page-briefs.md](page-briefs.md)。
> **角色视角**：AI 产品总监（产品定义 / 优先级 / 风险 / 验收）。
> **日期**：2026-09-12。

---

## 1. 背景与目标

### 1.1 一句话愿景

让 Artemis 用户在对话里一句话进入"设计现场"：**composer 选"设计"→ 结构化简报 → 看到多个差异化方案 → 微调/评审 → 一键实施成代码**——设计不再是工程师的斜杠命令，而是与计划/评审/执行平级的一等任务形态。

### 1.2 为什么是现在

- **竞品已验证范式**：Claude Design / Open Design 证明了"agent-native 设计循环"（发现 brief → 锁方向 → 流式产出 → 评审 → 交付）是真实需求，且其全部机制可被"提示栈 + 宿主协议 + 沙箱预览"复刻，不需要第二套编排框架。
- **Artemis 地基已就绪**：当前分支已落地一套引擎层完备的设计工作流（见 §2.1），安全模型甚至强于 OD（进程隔离预览、CAS 版本库、四重授权校验）。**短板不在引擎，在产品层**。
- **用户已有明确诉求**：本提案即来自"在 composer 新增设计模式来进入设计面板"的直接需求。

### 1.3 北极星指标

**设计模式周活跃采用率**（每周内至少一次进入设计工作流的本地任务占比）与 **设计→实施转化率**（产生 ≥1 个 revision 的设计文档中，最终触发"实施"的比例）。前者衡量入口是否成立，后者衡量闭环是否成立。

## 2. 现状基线

### 2.1 已有资产（`760c9db` + PR195 主线交付）

| 层 | 现状 | 评价 |
|---|---|---|
| 入口 | `/design` 斜杠命令、工作区 Dock"设计"tab、composer 徽章、workflow 变化后 1.5s 轮询自动开 tab | 可用但隐蔽；**composer 无档位化入口**是最大缺口 |
| 引擎 | Pi 唯一循环内：design turn 裁剪工具集（`design_document` / `design_save_revision` / `design_preview_check` + read 类），注入 `DESIGN_WORKFLOW_INSTRUCTIONS`（默认 3 差异化方案、上限 6 方案×10 页、`data-design-*` 契约、禁外网/eval/nested frame） | 与 OD 五阶段循环的"提示栈"路线一致，**架构方向正确，保持** |
| 安全 | 设计 turn 无 shell/write/MCP；Plan/Review 下写入全拒（`requireDesignExecute`）；broker 请求四重校验；主进程 `DesignService` 独立复核 | **优于 OD**，作为不变量保持 |
| 预览 | 独立 `WebContentsView` + 专属 session/partition + 三 URL 白名单协议 + CSP 禁网禁 worker + 进程隔离验证 + watchdog + 洪泛检测 | **优于 OD 的 srcDoc 沙箱**，保持 |
| 存储 | `design.sqlite` + 内容寻址 blob；revision 父链 + 冲突标志；版本化事件 envelope（`design.revision.saved`）；50 版/200MB 限额；操作幂等 | 契合 Artemis"版本化 envelope"不变量 |
| 检查 | `design_preview_check`：≤20 个点击/输入动作 + CDP 截图 + vision 模型判定，证据入库 | 评审的原料已有，**未产品化为可见循环** |
| 面板 | DesignPanel：工具栏/草稿条/任务队列/方案缩略条/画布+检查器(210px)/源码对比/静态导出/实施 | 功能全但**开发态**：原生控件、硬编码中文、轮询同步 |
| 草稿 | 双层草稿（localStorage + 主进程）+ 离开确认 + 保存前禁实施 | 机制好，有已知 bug（见 2.3） |

### 2.2 与 Open Design 对标的差距矩阵

| OD 机制 | Artemis 现状 | 差距定性 |
|---|---|---|
| SessionModeToggle 三档（chat/plan/design）+ 成本信号条 + 悬停说明卡 | 无 composer 档位，只有 `/design` 命令 + 徽章 | **核心缺口**（本提案主目标） |
| 意图 chip rail + 媒体面内联表单（composer 状态机） | 空态仅一个"开始设计"按钮 | 缺意图选择与示例引导 |
| question-form 简报协议（≤5 题、每题带默认、稳定枚举 id 回传） | `request_user_input` 工具已在白名单但未定义设计简报 | 协议已有雏形，缺产品定义 |
| direction-cards 方向卡（同构数据：用户点选卡 = agent 的 `:root`） | 变体（variants）即方向，已有缩略条 | 形态弱：小缩略图，非可选方向卡 |
| Critique wire protocol（多评委、composite 收敛、MUST_FIX=0） | 截图检查 passed/errors，无可见评审循环 | 缺产品化评审卡与收敛规则 |
| DESIGN.md + tokens.css 三层品牌包 + craft 手艺层注入 | 设计指令要求"先读 DESIGN.md/tokens"，但无项目级契约消费规范 | 缺正式契约与注入管线 |
| 版本历史模态（来源徽标 + 预览 + 非破坏恢复） | 版本 select + 源码对比 | 缺时间线/恢复体验 |
| 导出 PDF/PPTX/ZIP | 仅静态 HTML 导出 | 后置（P3） |
| `?screen=` 共享设备外框契约 | 无 | 后置（P3） |

### 2.3 已知债务（必须先还，见 P0）

1. **i18n MAJOR**：DesignPanel 与 App.tsx 设计 UI 全部硬编码中文（`i18n-resources.ts` 中 design 相关 key 为 0），英文用户看到中文。
2. **弃草稿 redo bug**：`DesignPanel.tsx:534-541` 丢弃草稿未清 `undone` 栈/operationId/主进程草稿，点"重做"可复活已丢弃编辑；且不派发 `artemis-design-drafts-cleared` 事件。
3. **键盘撤销绕过模式守卫**：Cmd+Z 路径不检查 `canWrite`（Plan/Review 下按钮禁用但键盘可改 patches）。
4. **控件体系**：面板用原生 button/select/input，未接 `@artemis/ui`（注意 Select options 重复值会抛错的前科）。
5. **轮询同步**：两处 1.5s setInterval 轮询（App/DesignPanel），应事件推送（技术债，非阻塞）。

## 3. 产品定义

### 3.1 目标用户与用户故事

- **主用户**：在 Artemis 里推进本地任务的工程师/技术 PM——想在动代码之前先看到界面长什么样，或想让 UI 改动先过自己一关。
- 用户故事：
  - US1 作为用户，我在 composer 选"设计"并一句话描述想法，就想看到 2-3 个差异化界面方案，而不是先读文档学 `/design`。
  - US2 作为用户，方案出来后我想直接在预览上点选改字改色改间距，不满意就退回重来，**不用担心误丢编辑**。
  - US3 作为用户，我想知道 agent 自己"看过"页面没有——检查通过与否要一眼可见，没通过要自动修一轮。
  - US4 作为用户，方案定稿后我要一键让它落成代码改动，且实施引用的是不可变版本，后续可追溯。
  - US5 作为英文用户，我要看到英文的设计面板（i18n 是发布门槛，不是美化项）。

### 3.2 心智模型：两维状态，一个入口

Artemis 内部有正交两维：**workflow（code/design）× runMode（plan/review/execute）**。产品决策（详见 §6 D1）：对用户呈现为**模式选择器里的第 4 个选项"设计"**——

```
计划 ○   评审 ○   执行 ○   ──────   ✦ 设计（进入设计面板）
```

- 选"设计" = `workflow: design` + `runMode: execute`，自动打开设计面板；
- 设计工作流内再选 计划/评审 = 设计的只读讨论（现有语义，徽章提示"设计 · 只读"）；
- 退出设计 = 面板"返回代码"按钮或徽章菜单（现有能力）。
- **不改 `RunMode` 协议枚举**——这是 UI 层的组合 affordance，协议保持正交稳定。

### 3.3 范围与非目标

**范围内**：composer 入口、空态引导、简报卡、方案画廊、版本时间线、检查评审卡、面板 i18n 与组件化、已知 bug 修复、DESIGN.md 契约消费、静态导出保持。

**非目标（v1 明确不做）**：
- ❌ 第二套 agent 编排（不变量：Pi 是唯一循环）；
- ❌ 自由画布/拖拽布局编辑（P3 已出界，保持）；
- ❌ 多评委评审剧场（OD 的 5 panelist；v1 用单评审官 + 收敛上限，P3 再评估）；
- ❌ 图片/视频/音频媒体生成（OD 媒体面不在范围）；
- ❌ PPTX/PDF 导出、设备外框库（P3）；
- ❌ IM 任务/无本地工作区任务的设计（现有安全边界，保持）；
- ❌ 内置 151 品牌设计系统库（版权与维护成本；但 DESIGN.md 格式与 OD 兼容，用户可自带）。

## 4. 解决方案总览（三层）

```
┌─ 入口层（用户怎么进来）──────────────────────────────────────────┐
│ composer 模式选择器第 4 项"设计" + 成本/预期提示 + 自动开面板        │
│ 空态：意图 chips + 示例 prompt + 一句话说明                         │
├─ 工作流层（进来后经历什么）───────────────────────────────────────┤
│ 简报卡（结构化 3-5 问，每题带默认值，可跳过）                        │
│ → 方案画廊（2-3 差异化变体 = 方向卡，缩略图 + 检查徽标）             │
│ → 预览 + 检查器微调（草稿双层保护，修复丢弃 bug）                   │
│ → 检查评审卡（passed/errors + 自动修复一轮，上限 2 轮）             │
│ → 版本时间线（父链/冲突/对比/恢复）→ 实施（不可变引用交接）          │
├─ 资产层（质量从哪来）────────────────────────────────────────────┤
│ 项目级 DESIGN.md 品牌契约（散文 + token，格式兼容 OD）注入设计 turn │
│ craft 手艺规则（anti-slop / 排版 / 可达性基线）按需注入              │
│ 语义化产物命名 + 写边界守卫（publication/stub guard 思路）          │
└──────────────────────────────────────────────────────────────────┘
```

**架构守则（映射 AGENTS.md 不变量，全部为"保持/复用"而非新增）**：
- Pi 唯一循环：设计循环继续由"系统指令注入 + 工具裁剪"驱动，不引入编排框架；
- UI 只消费 `@artemis/protocol`：新增的面板事件（简报/方向/评审）走版本化 envelope + 幂等 reducer，经 PiAdapter 之外的设计 IPC 通道（沿用现有 designState/designAction 模式）；
- Plan/Review 写入拒绝：保持 `requireDesignExecute`，新增 UI 一并遵守；
- 预览沙箱：`WebContentsView` 硬化模型不动；
- 测试先于任何边界放宽。

## 5. 分阶段路线图

### Phase 0｜卫生与地基（先还债，再盖楼）

**目标**：现有设计工作流达到"可对外展示"的质量底线。

| # | 条目 | 验收 |
|---|---|---|
| 0.1 | 修复弃草稿 redo bug（清 undone/operationId/主进程草稿 + 派发 cleared 事件） | 回归测试：丢弃后重做不可点、无复活 |
| 0.2 | 键盘撤销补 `canWrite` 守卫 | Plan/Review 下 Cmd+Z 无效果 |
| 0.3 | 设计 UI 全量 i18n（en/zh-CN，key 进 `i18n-resources.ts`） | typecheck + en 冒烟截图零中文残留 |
| 0.4 | 面板控件迁移 `@artemis/ui`（Button/Select/Dialog/TextField；Select options 唯一值） | 组件契约测试通过；无原生控件裸用 |
| 0.5 | （并行技术债）轮询 → 事件推送 | 设计状态变更 ≤200ms 反映到 UI |

### Phase 1｜产品入口（本提案核心交付）

**目标**：设计从"知情者命令"变成"一等模式"，US1 成立。

| # | 条目 | 验收 |
|---|---|---|
| 1.1 | composer 模式选择器加"设计"项（分隔线 + ✦ 图标 + 一行说明 + 用量较高提示），选中即 `workflow:design + mode:execute` 并自动开面板 | 无 `/design` 知识的新用户 30 秒内完成首次进入（可用性测试） |
| 1.2 | 徽章升级：设计工作流激活时 composer 左侧显示"设计"徽章（点击跳面板；菜单含"返回代码"） | 切换语义零歧义（用户测试 5/5 正确说出当前处于设计） |
| 1.3 | 设计内切 计划/评审 的语义提示：徽章变"设计 · 只读"+ toast 一句话解释 | 误操作率（设计内切模式后立即退出）< 5% |
| 1.4 | 空态重做：意图 chips（网页原型/移动原型/组件/着陆页/后台界面/自由探索）+ 每 intent 2-3 条示例 prompt + "开始设计" | 空态点击率（进入后 7 天内发出首个设计请求的用户占比）≥ 60% |
| 1.5 | 入口不可用态：IM/无本地工作区任务中"设计"项禁用 + 原因 tooltip | 无死按钮 |

### Phase 2｜设计循环质量（简报 → 方向 → 评审）

**目标**：把 OD 验证过的循环产品化，US2/US3 成立。

| # | 条目 | 验收 |
|---|---|---|
| 2.1 | 设计简报卡：首次设计 turn 由 Pi 经 `request_user_input` 发结构化简报（意图确认/平台与尺寸/保真度/品牌参考，≤5 题每题带推荐默认，可整体跳过）；答案以稳定枚举 id 回传 | 简报完成率 ≥ 70%，跳过率 ≤ 30%；跳过也能出方案 |
| 2.2 | 方案画廊升级：变体从 240px 缩略条升级为方向卡（检查截图 + 名称 + 一句差异描述 + 通过/未检徽标），点击切换画布 | 用户在画廊的平均浏览变体数 ≥ 2 |
| 2.3 | 检查评审卡：`design_preview_check` 结果产品化——会话/面板内显示 passed ✓ / errors 列表；未通过自动追加修复 turn（上限 2 轮，超出交回用户） | 检查覆盖率（有 revision 且跑过检查）≥ 90%；一次修复通过率 ≥ 50% |
| 2.4 | 版本时间线：版本 select → 时间线弹层（父链、冲突分支、来源徽标 ai/手动、预览、对比、恢复=写新版本） | 恢复操作零历史丢失（回归测试） |
| 2.5 | 项目 DESIGN.md 契约：项目根可选 `DESIGN.md`（散文 + `:root` token 块，格式兼容 OD）；存在时注入设计指令并禁止 agent 发明体系外 token；basis 记录读取 | 带 DESIGN.md 项目产物的 token 溯源率 100%（抽查） |
| 2.6 | craft 手艺层：3-5 条品牌无关规则（anti-slop 清单/排版基线/对比度基线）注入设计指令 | 产物 slop 特征（紫渐变/emoji 图标等）人工抽检显著下降 |

### Phase 3｜规模化与增味（按数据决策，另立项）

方向池（不做承诺）：静态导出之外的 PDF（Electron printToPDF）；`?screen=` 式设备外框契约；设计草稿沉淀为项目模板/画廊；多评委评审剧场；方向卡升级为 OD 式同构数据（用户点选卡 = agent 的 `:root`）；Windows 设计工作流验证矩阵补齐（发布门槛，见 §7）。

## 6. 关键产品决策记录（PDR）

| # | 决策 | 推荐方案 | 理由与被否方案 |
|---|---|---|---|
| D1 | "设计模式"挂在哪一层？ | **workflow 维**（UI 呈现为模式第 4 项），不改 `RunMode` 协议枚举 | 两维正交是既有架构；改枚举波及协议/校验/埋点全链路（OD 报告的 18 处改动教训）且混淆语义。被否：给 RunMode 加 `design` 值 |
| D2 | 简报卡走什么协议？ | P1 用 Pi 现有 `request_user_input`（已在设计白名单）+ 设计简报规范写进 `DESIGN_WORKFLOW_INSTRUCTIONS`；富方向卡（带色板/字体样例）P2 再作为版本化 protocol 事件 | 零新协议面即可交付；OD 的 question-form 精髓（默认值/题上限/稳定 id）以规范而非新 schema 落地 |
| D3 | 品牌契约用什么格式？ | 项目根 `DESIGN.md`（散文 + `:root` token），**格式兼容 OD**，用户可直接把 OD 品牌包放进项目 | 不自造格式（生态复用）、不内置品牌库（版权/维护）。被否：内置 151 品牌包 |
| D4 | 评审做多深？ | 单评审官（现有 vision 截图检查）+ 自动修复 1 轮 + 上限 2 轮 + 结果卡 | OD 多评委剧场的收敛规则（阈值 + MUST_FIX=0 + 字节递减）值得借鉴但其成本/延迟不适合 v1；先验证"看得见的检查"价值 |
| D5 | 导出范围？ | v1 保持静态 HTML；PDF 列 P3 | 导出是交付端锦上添花，入口与循环才是价值主干 |
| D6 | 组件与文案门槛？ | P0 强制：`@artemis/ui` 全覆盖 + i18n 全量 | 设计面板是"设计产品"的门面，原生控件+中文硬编码损害产品可信度；且 Select 崩溃前科要求组件统一 |
| D7 | 同步机制？ | P2 换事件推送，不阻塞产品面 | 轮询不影响用户可感知的正确性，属技术债 |
| D8 | 覆盖哪些任务？ | 仅本地桌面任务（现状保持） | 安全模型绑定本地工作区与进程隔离预览；IM 边界是架构不变量 |

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| "设计"与"执行"模式语义混淆（用户以为选执行=退出设计） | 高 | 徽章常驻 + 只读态明示 + D1 的菜单内提示；用户测试先行 |
| vision 模型不可用/降质 → 检查卡空转 | 中 | 检查不可用时降级为"未检查"徽标 + 一键重试；不阻塞产出 |
| 设计指令 token 预算膨胀（简报+DESIGN.md+craft 叠加） | 中 | 借鉴 OD "push 核心契约、重文件按需 read"；DESIGN.md 超 12K 截断并提示 |
| 版本/冲突分支 UI 复杂度失控 | 中 | 时间线首版只读 + 对比；"恢复写新版本"复用现有 CAS 语义 |
