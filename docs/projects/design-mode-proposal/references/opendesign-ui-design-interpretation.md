## 一、产品是什么：一份"集成外壳"的设计哲学

项目的原点文档 `docs/spec.md`（已归档）给出了定调性的一句话：**把自然语言 brief 变成可编辑、可预览的设计产物，方式是编排用户机器上已安装的 coding agent**。它刻意不做的事和做的事同样重要：不拥有 agent、不拥有模型、不拥有技能目录——三者全部外部可插拔（Claude Code / Codex / Cursor 等 + BYOK），OpenDesign 只做 "substrate（底座）"。产物不是画布二进制，而是**真实代码**（HTML/CSS/组件），可导出 HTML / PDF / PPTX / MP4，也可直接丢进 Cursor 继续开发。

用户旅程被抽象成一个五步心智模型：**discover the brief → lock the direction → stream the artifact → critique → deliver**。所有界面交互设计都是围绕这条循环展开的。

⚠️ 阅读时注意权威层级：`spec.md` 和 `architecture.md` 均已标注归档/部分过时（如 spec 说不做桌面应用，现实已是 Electron 桌面端）；**当前行为的权威源是根 `README.md`、各级 `AGENTS.md`、`specs/current/` 和代码本身**。

## 二、界面总体结构

顶层五个页面，职责清晰：

| 界面 | 职责 |
|---|---|
| **Home** | 选产物类型（原型/幻灯片/图片/视频/音频…）、写 brief、发车前配好设计系统/模型 |
| **Plugins** | 浏览官方工作流目录，点 "Try it" 直接起任务 |
| **Design System** | 提取品牌视觉语言成 `DESIGN.md`（9 节 schema），在同一工作区使用它 |
| **Studio**（核心工作区） | **对话 + 文件列表 + 实时预览三者常驻同屏**，六种产物各有专属预览形态（原型可交互、幻灯片多页缩略图、移动端带设备框…） |
| **Settings** | 本地 CLI 探测（Rescan）、BYOK、MCP 配置 |

Studio 里跑一次生成（一个 Run）有两种执行剖面，直接决定用户看到什么：**Filesystem 型** agent 写真实项目文件，文件事件实时刷新预览；**Text-artifact 型**（纯文本流/BYOK）把整个产物作为 `<artifact>` 源码块吐出，由 host 解析后进入同一套预览管线——用户视角殊途同归。

## 三、聊天面板：全部交互设计的重心

这部分是文档投入最大的地方——主规格 `specs/current/chat-panel-next.md` 超过 160KB，记录了 24 个组件、84 个状态、50+ 条编号设计决策（D 系列），基线是一份 1:1 对齐的交付稿，配套陈列页 `docs/design/chat-mirror/` 可直接打开对照。

### 一轮消息的解剖（自上而下固定顺序）

1. **用户消息气泡** + 附件行；记忆卡紧跟其后（不排轮末）
2. **壳 1（执行记录）** 钉在本轮正文上方：装下探路期的 thinking、工具调用、过程叙述。最多两张壳
3. **壳 2（有清单时）**：一行「执行计划 · N 步」+ **每条 todo 一个抽屉**；清单期间的所有输出都收进"当前进行中"的那条抽屉里
4. **产物卡**：往文件写入的那一刻就出现（灰占位呼吸闪烁），run 结束才定格；整卡即预览入口，右上角「发布/导出」
5. **结论正文**：done 之后回到壳外，逐字化开入场
6. **轮末**：产物卡 → 总结 → 状态行（赞/踩/复制/Fork）→ 下一步引导（点一条=直接发出那句话）

最核心的决策是 **D29**：过程（thinking/工具）和结论严格分流——过程进壳、结论在壳外，"执行记录永远出现，不等 agent 信号"。这解决的是 AI 产品最常见的痛点：**流式输出时用户分不清"它在干活"还是"它说完了"**。

### 几个精心打磨的交互细节

- **Plan Pill（计划胶囊）**：输入框上方一枚「第 N / M 步」药丸——N 是*正在做第几步*而非*已完成几步*；悬停向上浮出完整清单，与执行记录共用同一套状态记号（绿球=进行中、绿勾划线=完成、虚线圈=未开始）。它被刻意挂在 `.chat-log` 滚动容器**外**，且必须接 `containerRef + ResizeObserver + MutationObserver` 三件套，否则会挡住新消息自动滚动。run 结束或清单清空，整枚消失。
- **旧版固定 Todo 卡片被明确废除**（B17）：任务清单只在执行记录里出现**恰好一次**，不再"钉住的卡 + 消息流里的卡"两处重复。
- **`<question-form>` 澄清问题**：模型在正文里内联发出表单 artifact，渲染在**产生它的那条助手消息内部**；答案作为下一条用户消息回流（不画新气泡，因为摘要已长在上一条消息上）。明确不做独立的 Questions Tab——**对话即界面**。
- **流式逐字动画**：只给新到的字挂入场动画、每帧拆掉上一帧的、永不动 React 节点；判据必须看可见文本 diff 而非 delta 长度（曾因 delta 落在隐藏标记里导致 641 帧中 358 帧重放）。流式光标被刻意删除。
- **工具调用去重**：TodoWrite 这类快照式工具按"每次调用=全量状态替换"折叠，只有最新一次存活；同一调用从"在跑"到"跑完"必须是同一行换状态。
- **空壳规则**体现"降级是一等公民"：跑完的空壳删、失败的空壳留（壳头是唯一报事的地方）、无内容不给展开箭头、无耗时不用 `0s` 占位。

### 错误交互：一份教科书级的设计

`docs/design/run-errors/error-ux-design.md` 用 32 个场景（S01–S32）逐个写清"什么时候出现/出现在哪/长什么样/点了之后怎样"，并按真实失败数据排优先级（14 个场景覆盖 93.3% 失败）。五条原则值得全文背诵：

1. **能在发送前知道的，不让发**——没装 agent、没登录、没余额，都在点发送时拦住，不产生失败
2. **系统能自己救的，不打扰**——限速、断线自动重试，用户最多看到一行"正在重试 2/2"
3. **等待要有回音**——60 秒无输出转为"上游响应慢，已等 N 秒"，10 分钟才判死
4. **"重试"只在有用时出现**——额度用完给〔更换模型〕而不是骗人的〔重试〕
5. **文案说人话、不怪用户、给下一步**

还有细腻的容错语义：断线时若已有输出则不自动重试（避免毁掉半成品），改给〔继续运行〕从断点续跑；文件已生成但进程报错→**算成功**，只附一行"过程中报过错"。

## 四、画布交互：直接操纵编辑（Direct Manipulation）

这块已完全交付且相当成熟（v2.4 Playwright 真浏览器验收 20/20 通过），规格在 `specs/current/manual-edit-direct-manipulation.zh-CN.md`。

**四个模式，边界硬**：Edit（纯手动，**绝不自动调 AI**）/ Comment AI（选中画布元素写指令，唯一 agent 编辑路径，agent patch 源码后用户审查）/ Tweaks（全局 token 微调）/ Draw（纯视觉批注）。源文件是唯一真源，一切画布操作最终都落成源码 patch。

**已交付的画布能力**：点选元素出蓝框+浮动动作条、宽度拉伸（inline 自动升级 inline-block）、自由移动（红色虚线对齐参考线+5px 吸附）、行内文字编辑+浮动工具栏（Manus 风格取色器）、图片替换/裁剪/等比缩放、⌘Z/⇧⌘Z 撤销重做、Cmd+C/V 复制粘贴元素、OS 文件拖放插入。交互语义做了精化：**首击只选中，二击或双击才进编辑**（修掉"一选中就变大"的抖动）。

底层是**六层体系**（身份标注 → 选中 chrome → 样式预览管线 → 内容原地补丁 → 版本历史 → 外部同步），两个关键不变量：样式管线**永不重载 iframe**（预览→防抖→落盘）；每个手势 = 一条历史 + 一个语义化文件版本。与 AI 的协同闭环设计得很优雅：编辑模式开着时，agent 的外部改写通过 frozen-source 生命周期"**交互中推迟、空闲即跟随**"——手动改动实时落盘 → AI 基于其上改 → Edit 再基于 AI 结果继续。

**工程底座**是双轨渲染：普通预览走 URL iframe，编辑/批注/微调走 srcDoc 注入 iframe，**两个 iframe 常驻同挂、切 visibility 而非重挂载**（消灭切换闪白），五条 postMessage 桥（edit / comment / palette 换肤 / deck 翻页 / tweaks 面板）各司其职。

## 五、进行中的规划（尚未落地）

- **视觉发现**（`specs/current/studio-chat-visual-discovery.md`）：用数据指出现状痛点（24.3% 新项目首轮被提问、85% 的 skip 是倒计时超时被动跳过），方案是动态提问（信息完整直接生成）+ 看图选风格（每风格绑定结构化 styleSpec 注入 agent 上下文）+ 问题内联在 Chat 流中原地折叠成 "Brief 已确认" 摘要
- **回复信息架构**（`specs/current/studio-chat-response-information-architecture.md`）：把回复从"事件流水"重组为**任务视图**——回合摘要/任务组/产物/异常/下一步，已完成折叠、失败保持展开
- **流式滚动**（`specs/current/chat-stream-scroll-research.md`）：结论是不引库，现有实现 8 条难点中 5 条已是同行最好，补齐键盘意图识别、程序滚动标记、0.5px 亚像素死区等缺口

## 六、贯穿全文的设计理念总结

1. **对话即界面**：没有独立的任务面板/问题面板，一切（清单、提问、产物、错误）都长在对话流里，且每样东西只出现一次
2. **降级是一等公民**：没有数据就不占位、不伪造（无耗时不用 `0s`、被打码就写"输出不可见"）——因为 8 家 agent 能力参差，基线形态是平铺，分段是增强
3. **状态诚实**：被取消的任务不谎报完成、停掉的 pending 工具不转圈、做了一半明确说"还有 N 项未完成"
4. **纯函数管逻辑、组件只管画**：归属判定全在 `runtime/chat/` 纯函数层，这是 24 组件 × 84 状态还能维护住的原因
5. **文档与代码同责**：改交互必须同步改规约（"改代码不改规约 = 下一个人按规约把它加回来"），决策全部编号留痕，定了的事不留开关
