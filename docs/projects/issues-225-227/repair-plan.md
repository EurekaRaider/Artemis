**4. #225：任务级授权与本地审批复用**

产品行为：首次需要授权时，在同一个授权视图中说明目标应用、有效范围和是否允许前台操作。用户可以只允许本轮，也可以明确选择“允许本任务自主操作此应用”；前台许可由用户单独选择。内置浏览器不展示原生前台选项。已有应用访问许可时，只补充缺失的任务或前台许可。

“本任务自主操作”表示：该任务在该应用内完成用户请求时，由当前模型随工具调用给出风险判断，再由宿主按现有审批规则决定执行。它不代表应用中的任意操作都已获得业务授权。

授权结构与生命周期：

| 对象                 | 绑定范围                           | 有效期与失效规则                                                                           |
| -------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| 已有持久应用访问许可 | 应用身份                           | 保留原有含义，可在设置中撤销；不隐式授予前台或任务自主操作                                 |
| 本轮许可             | 任务、轮次、应用                   | 轮次结束即失效                                                                             |
| 新增任务许可         | 任务、稳定应用身份、用户选择的能力 | 同一运行会话内跨轮保留；撤销、任务归档／删除、禁用或卸载插件、切离 Execute、退出应用时清除 |
| 实际控制租约         | 任务、轮次、当前目标               | 每轮重新建立，停止或轮次结束立即释放                                                       |
| 动作票据与观察       | 当前调用、精确参数、当前观察       | 继续沿用现有单次票据与过期校验                                                             |

原生应用使用核实过的 bundle ID 关联任务许可，实际输入仍核对当前 PID、窗口和目标；浏览器许可限定本任务拥有的浏览器。授权由宿主保存，模型参数不能创建或扩大许可。

实现步骤：

1. 在 `ComputerUseHost` 中增加任务许可及明确的生命周期清理，与现有本轮和持久应用许可分开管理。任务许可先保存在内存，不把临时前台权限持久化到下一次启动。
2. 授权成功时记录所选范围和能力；统一处理待确认对话框，避免同一目标的并发请求重复弹窗。
3. 主进程只对有效任务许可覆盖的内置 Computer Use 调用，使用现有代理审批判断；全局审批设置和其他工具的行为保持原有语义。
4. 对 `computer_act` 从宿主掌握的租约中解析实际目标，确认归属后再复用许可，不能只相信模型提供的目标名称。
5. 每次工具调用继续携带现有 `model_approval`。高风险动作仍要求明确属于用户请求；不能凭“有任务许可”自动把该字段改成真，也不能把所有点击改为低风险。
6. 超出目标、前台能力或操作授权范围时，请求对应的一次决定；拒绝后返回明确状态，避免模型在同轮反复请求相同许可。
7. `endTurn` 释放控制和截图状态，保留有效任务许可。Stop 暂停控制；Resume 只解除暂停，后续重新打开并观察。撤销则同时删除许可、关闭待授权流程并取消正在执行的输入。
8. 在现有控制条／权限入口显示“本轮／本任务／持久应用访问”和“后台／可前台”，支持准确撤销。复用既有审批记录，记录许可来源、范围和本地放行结果，不记录按键正文或截图内容。

审批路径的性能契约：

`模型一次生成动作及 model_approval → 宿主核对任务和目标 → 本地检查许可和既有风险规则 → 执行并返回结果`

审批单独触发的模型请求数必须为 **0**。用户交互只出现在缺少许可、超出授权或现有风险规则要求决策时。普通的“观察—模型决策—动作—结果”往返依然存在。

批处理优化范围：

- 复用现有最多 8 步、授权后 3 秒的动作批次，不扩大限制。
- 已知且可连续执行的控件点击、填写合并调用；直接使用动作返回的新观察，避免无必要的 `computer_observe`。
- 坐标点击、导航、弹窗和界面变化继续遵守现有提前停止与重新观察规则，不要求所有动作都强行凑成八步。
- 同步工具描述、内置技能和产品说明，使授权与批处理的实际行为一致。

验收：

- 同一应用获得任务许可后，多次常规动作和新一轮操作不再重复询问同一许可。
- 授权范围内、符合既有模型审批规则的调用不出现额外审批卡片；新增审批模型调用数为 0。
- “只允许后台”不会被坐标点击、按键或滚动升级为前台；明确允许前台后跨轮复用该许可。
- 其他任务、其他应用、子代理和伪装的同名 MCP 服务不能复用许可。
- 旧持久许可保持原义；未选择新授权时保留现有审批行为。
- Stop、撤销、模式切换发生在等待授权或执行中时，后续动作不再下发。
- 每轮仍使用新的租约和观察，旧截图、旧票据、旧轮次请求被拒绝。
- 在本地固定表单中，多个已知字段可单批完成；提交等动作按现有规则独立处理。

主要改动位置：`computer-use/host.ts`、`computer-use/service.ts`、`main.ts` 的审批和任务生命周期接入、`ComputerUseControls.tsx`、共享权限类型和文案。只添加必要的 Computer Use 定向接入，不重写通用审批系统。`Full local access` 仍仅影响可执行扩展。

**5. #226：证据驱动的原生暂停修复**

先建立可重复案例，再确定补丁。当前不能把“自身输入标记丢失”“授权点击延迟到达”或“Codex 特殊行为”写成已确认根因。

第一步：定位首次暂停。

- 记录真实 Artemis 版本、原生助手版本、macOS 与架构，确认运行的是预期二进制。
- 记录请求的应用身份和实际返回的 bundle ID、PID、窗口标识，核对 Issue 中应用名与窗口名的差异。
- 增加小范围、可关闭的诊断，记录事件类型、来源进程、自身注入标识、单调时钟时间、控制会话及前后台状态，不记录输入文本或窗口内容。
- 将“系统权限不足”“前台许可未授予”“实际输入接管”“原生助手退出／超时”分开记录，保留第一个失败原因。
- 依次复现临时原生测试应用、Codex 前台坐标操作、连续输入、授权之后的首次动作，以及暂停后的重试。Codex 使用测试会话或草稿，不发送消息。

第二步：依据证据选择最小修复。

| 复现结果                                 | 对应处理                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 自身注入被当成用户输入                   | 修正自身事件识别与注入关联；用实际事件来源和当前控制会话验证，不仅凭动作发生的时间接近而忽略事件 |
| 授权之前产生的旧事件在获得控制后才到达   | 在一致的单调时钟上判断事件归属，只排除确实早于本次控制的旧事件，不增加任意时长的忽略窗口         |
| 前一目标、租约或助手的延迟回调影响新控制 | 绑定控制会话与目标身份，拒绝过期回调，释放时清理相关状态                                         |
| 确有新的人工输入                         | 保持暂停行为，改善原因及恢复提示，不以“误判修复”屏蔽真实接管                                     |
| 实际目标、窗口或权限异常                 | 修正被证实的目标／权限处理，返回对应原因，不继续归类为用户输入                                   |

若现有二进制和可靠复现步骤中没有误判，则交付复现证据和正确的恢复路径，不提交没有证据支撑的输入策略放宽。

与 #225 联合处理：应用授权、前台授权以及动作审批可能产生真实确认点击。需要验证这些输入在“等待授权→获得控制”的时间边界上不会变成错误的接管事件；控制已经生效后的真实用户输入仍立即暂停。

验收：

- 临时原生应用和 Codex 在无人输入情况下可连续执行被授权的前台操作，无误暂停。
- 自身生成的点击、按键、滚动不触发接管；真实人工输入和 Stop 仍停止后续动作。
- 后台控制时，在其他应用操作不误暂停；前台控制时，用户输入优先。
- 刚完成授权的首次动作成功；过期会话事件不影响新目标。
- 暂停后同轮重开仍不能绕过暂停；Resume 后必须重新观察，旧观察不能直接执行。
- 原生助手退出、超时、系统权限撤销分别给出准确原因。
- 使用同一应用版本、同一脚本重复测试并保存结构化证据。未完成原生复现时，本项保持“未验证”，单元测试通过不作为关闭依据。

主要改动位置：`native/computer-use/main.swift`、`input-policy.swift`、`computer-use/native-driver.ts`、`service.ts` 和原生验证夹具。具体文件以复现结果为准。

| 观察、停止和控制反馈                       | 按已有目标检查：观察 p95 ≤1 秒、停止 ≤500 毫秒、控制反馈 ≤100 毫秒；报告实测值及环境 |

模型正常决策耗时单独报告。不能用本地审批很快或截图很快替代端到端流畅度验证，也不承诺消除正常模型往返。

**8. 实施顺序与交付**

1. **冻结基线与补测试**：确认三个 Issue 当前状态、保留已有工作，补充图标、授权与暂停复现用例。
2. **修复 #227**：来源解析、卡片图标和状态展示，独立验证并形成可审查的提交。
3. **定位并处理 #226**：在原有授权行为下取得首次暂停证据，完成适用的原生修复，先确认 Stop／Resume 可靠。
4. **实施 #225**：任务许可、现有本地模型审批接入和界面说明；验证新授权流程与原生接管时序。
5. **联合验收**：跨轮操作、批处理、授权确认、实际接管、历史图标与完整回归。

按上述范围拆分提交，便于审查和单独回退。#227 可独立交付；#225 与 #226 必须完成联合时序验证。若 #226 尚未找到稳定复现，保持该项未验证，不将其余修复通过表述成三个 Issue 全部解决。

交付内容：源码补丁、必要回归测试、更新后的 Computer Use 文档与工具说明、测试结果、UI 证据、原生复现及性能记录。发布时另按项目现有流程完成正式 macOS arm64／x64 包及签名、公证等验证；本计划中的开发机结果不代替发行验收。

**9. 用户审核项**

本计划建议批准以下产品行为后开始实施：

- 插件品牌图标在运行、完成和失败时保留，状态单独展示。
- 用户可明确授予“当前任务＋指定应用”的自主操作许可，并单独选择是否允许前台；该许可跨轮复用，在当前应用运行会话内有效且可撤销。
- 有效任务许可覆盖的 Computer Use 操作复用现有模型风险判断，由宿主本地决定，不新增审批模型请求；该选择不改变其他工具的全局审批模式。
- #226 以原生事件证据确定修复，真实用户接管与停止能力继续作为必须通过的验收项。

用户已批准以上范围；实施不包含发布、推送或关闭 Issue。
